# VM Compare South Africa — v1 Plan

**Goal:** Answer one question better than anyone else: *what is the cheapest VM you can get in a South African data centre?*

A fast, static, SEO-first comparison site that shows the best value VPS plans in South Africa, tracks prices weekly, and stores price history per provider.

- **Production URL:** `https://vm-compare.fixes.co.za`
- **Repo:** `git@github.com:aral190/vm-compare.git` (public, default branch `main`)
- **Design:** clean data-first light theme, one accent colour, dense readable table
- **Status:** v1 includes frontend, scraper, history and weekly automation

---

## 1. Product scope

### Pages

| Page | Purpose |
|---|---|
| `/` | Hero, cheapest-per-tier winners, full interactive table, last-updated date |
| `/cheapest-{n}gb-vps-south-africa/` | Generated SEO landing page per RAM tier |
| `/providers/` | Index of every tracked provider |
| `/providers/{slug}/` | Plans, features, reputation notes, price-history chart |
| `/methodology/` | How prices are normalised and ranked |
| `/faq/` | Common questions, marked up with `FAQPage` |
| `/about/` | Who runs the site, editorial policy |
| `/suggest-a-provider/` | Prefilled `mailto:` for providers wanting to be listed |

### Homepage UX

- Winner cards for 1, 2, 4, 8, 16 and 32 GB tiers.
- Full table, server-rendered, with filters:
  - RAM: 1 / 2 / 4 / 8 / 16 / 32 GB
  - Minimum vCPU
  - Storage type: NVMe / SSD / any
  - Provider
  - Monthly billing only
- Sort by price, price per GB RAM, or resources.
- URL-synced filter state (`?ram=4&vcpu=2&storage=nvme`) so views are shareable.
- "Best value" and "price dropped" badges.
- Mobile: table collapses into cards.
- Tables are rendered in HTML; client JS only shows/hides rows. No framework, no JSON fetch, no layout shift.

### Qualitative signals

Price per resource is the primary ranking. Secondary badges and notes cover:

- NVMe vs SSD vs HDD
- Backups included
- One-click installs / app templates
- Support level and channel
- Provider reputation and years operating
- Data-centre location (Johannesburg / Cape Town / elsewhere)
- Dedicated IPv4, bandwidth, setup fees

## 2. Data model

### Provider

`data/providers.json`

```json
{
  "slug": "rackzar",
  "name": "Rackzar",
  "website": "https://rackzar.com",
  "pricingUrl": "https://rackzar.com/vps-hosting/",
  "category": "sa",
  "locations": ["Johannesburg", "Cape Town"],
  "vat": "excl",
  "adapter": "html",
  "features": ["nvme", "backups", "one-click-installs"],
  "reputation": "Proxmox partner, local support, 400 Gbit peering.",
  "affiliateUrl": null,
  "notes": ""
}
```

`category` is `sa` (South African provider/hosting) or `international` (JNB region, kept in a separate section).

`vat` is `incl`, `excl`, or `unknown`.

### Plan

`data/plans.json` — current normalised plans, generated by the scraper.

```json
{
  "id": "rackzar-4-2-60",
  "provider": "rackzar",
  "plan": "VPS 2GB",
  "vcpu": 4,
  "ramGb": 2,
  "storageGb": 60,
  "storageType": "nvme",
  "bandwidthTb": null,
  "priceInclVatCents": 22885,
  "priceAsListedCents": 19900,
  "vatIncluded": false,
  "billingTerm": "monthly",
  "setupFeeCents": 0,
  "ipv4": 1,
  "location": "Johannesburg",
  "features": ["nvme", "backups"],
  "url": "https://rackzar.com/vps-hosting/",
  "lastChecked": "2026-11-09",
  "status": "current",
  "source": "seed"
}
```

Rules:

- Money is stored as integer **cents** in ZAR to avoid floating-point errors.
- `priceInclVatCents` is the canonical comparison price.
- `priceAsListedCents` preserves what the provider advertises.
- Annual-only pricing is converted to an effective monthly price and flagged `billingTerm: "annual"`.
- Promotional first-month pricing is excluded unless no renewal price is available; then it is flagged in `notes`.
- Failed scrape: keep the last good plan, set `status: "stale"`, update `lastChecked` only after a successful check.
- VAT rate: 15%. `excl` prices are multiplied by 1.15 and rounded to the nearest cent.

### History

`data/history/{provider}.json`

```json
[
  {
    "date": "2026-11-09",
    "plans": [
      { "id": "rackzar-4-2-60", "priceInclVatCents": 22885, "vcpu": 4, "ramGb": 2, "storageGb": 60 }
    ]
  }
]
```

One snapshot per provider per scrape run. Used for sparklines, price-drop badges and the updates feed.

### Overrides

`data/overrides.json` — manual corrections for ambiguous promotions or pages that can't be scraped reliably. An override pins a plan's fields and records who/why.

## 3. Architecture

```
astro.config.mjs
package.json
public/
  CNAME                        # vm-compare.fixes.co.za
  robots.txt
  favicon.svg
src/
  components/                  # FilterBar, PriceTable, PlanCard, Sparkline, Badge
  layouts/Base.astro
  lib/                         # data loading, formatting, SEO helpers
  pages/                       # index, tier pages, providers, methodology, faq, about
  styles/global.css
data/
  providers.json
  plans.json                   # generated
  overrides.json
  history/<provider>.json
  snapshots/                   # raw scrape output, date-stamped
scripts/
  scrape.ts                    # CLI: --all | --provider=x | --dry-run
  adapters/                    # html (fetch+cheerio), playwright, manual
  normalize.ts                 # VAT, billing term, units
  validate.ts                  # Zod schemas
  history.ts
.github/workflows/
  deploy.yml                   # push -> build -> GitHub Pages
  update.yml                   # weekly cron -> scrape -> validate -> commit -> deploy
```

### Stack choices

- **Astro** static output. Zero client framework.
- **Hand-written CSS** with design tokens (no Tailwind build step, no reset bloat).
- **Vanilla JS** filter island, under 5 KB.
- **TypeScript** across site and scraper so the plan schema is shared.
- **Zod** validation so bad scrapes fail loudly.
- **fetch + cheerio** for static pricing pages; **Playwright** only for JS-heavy pages.
- **GitHub Actions** for scheduled scraping and deployment.

### Scraper design

Each provider gets an adapter implementing:

```ts
interface Adapter {
  slug: string;
  fetchPlans(): Promise<RawPlan[]>;
}
```

Adapters:

| Type | Used for | Method |
|---|---|---|
| `html` | Static pricing tables | `fetch` + `cheerio` with CSS selectors |
| `playwright` | JS-rendered configurators | Headless Chromium |
| `manual` | Ambiguous or protected pages | Read `data/manual/{slug}.json` |

Every adapter run is isolated: one broken provider must not fail the whole scrape. The CLI prints a per-provider summary and exits non-zero only if every provider fails.

### Weekly automation

`update.yml`, Monday 06:00 SAST:

1. Checkout, install Node 22 and dependencies.
2. Run `npm run scrape`.
3. Run `npm run validate`.
4. Commit changed files under `data/` with a dated message.
5. Build and deploy to GitHub Pages.
6. Failed run leaves the live site on the last good data.

`deploy.yml` builds and deploys on every push to `main`.

## 4. SEO and performance

- Static HTML for every page; no client-side rendering of primary content.
- Canonical URLs, Open Graph and Twitter cards.
- `sitemap.xml` via `@astrojs/sitemap`, `robots.txt` pointing to it.
- JSON-LD: `WebSite`, `ItemList`, `Product`/`Offer`, `FAQPage`, `BreadcrumbList`.
- Internal linking between RAM tiers, providers and methodology.
- Descriptive title tags targeting "cheapest VPS South Africa", "1GB VPS South Africa", etc.
- Fast by construction: inlined critical CSS, one small font subset, SVG only, no images above the fold.
- Target Lighthouse: 95+ performance, 100 accessibility, 100 SEO.
- Google Search Console + Bing Webmaster Tools verification.
- Optional privacy-friendly analytics (Plausible or Cloudflare Web Analytics) added later.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Scraping breaks when a provider redesigns | Per-provider adapters, fixtures, last-good data + `stale` flag |
| JS-heavy or bot-protected pricing pages | Playwright adapter, then manual override with review |
| VAT / billing-term apples-to-oranges | Normalise to incl. VAT and effective monthly; store original |
| Promotional pricing distorts rankings | Exclude intro-only prices; flag when unavoidable |
| History files grow large | One snapshot per provider per run, compact fields, prune to weekly after a year |
| Site depends on GitHub Actions | Build is reproducible locally; any static host can serve `dist/` |
| Email address is unmonitored | Clear contact page; consider a forwarder/alias |
